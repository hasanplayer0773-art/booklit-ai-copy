### [STEP-6.3] In-App Preview, Job History & Undo/Redo

#### 1. Rationale

Three requested features — Live Preview, Job History, and project-level Undo/Redo — share a common architectural question the existing two-tier state model (STEP-1.1's lightweight Qt Signals vs. heavy `DocumentStore`+`RLock`) does not yet answer: where does state that outlives a single job, or that must be inspected before InDesign is ever invoked, actually live? This step resolves that question once, rather than three times inconsistently.

**Post-review correction:** the original draft had a direct, confirmed contradiction — it stated Undo/Redo "never acquires `DocumentStore`'s `threading.RLock`" while also stating undo "restores `raw_content` within `DocumentStore`," which is not achievable safely at the same time (a mutation of protected state must go through the lock protecting that state). It also used a single `undone` boolean flag, which cannot correctly represent linear undo→redo→new-edit history (branching); left `source_file_hash`'s meaning ambiguous (binary file hash vs. STEP-1.1's normalized-text hash, which are different values computed differently); and did not define what happens when a previously-edited job is reopened after the application restarts. All four are corrected below.

#### 2. Architectural Decision

- **Live Preview reads directly from the existing in-memory `DocumentStore`** for the currently-open job — it requires no new persistent storage, since it only needs to render the already-extracted, already-classified `BookletDocument` tree (STEP-1.1's Pydantic models) before the COM/InDesign step runs. This keeps Live Preview fully decoupled from InDesign: it can render from `ContentBlock`/`PageData`/`TableData` alone. **The `RLock` is held only long enough to copy an immutable snapshot of the page(s) being rendered; the lock is released before any Qt painting, layout, or PDF-rendering work begins** — rendering a large page while holding the lock would block classification updates, edits, undo, and job-progress signals for the duration, which is unacceptable given `DocumentStore` is shared across the whole application.
- **Job History and Undo/Redo require state that outlives a single job's `DocumentStore` lifetime**, and are both, by nature, structured local records — the same profile that motivated `sqlite-vec` for STEP-3.1's question bank (single-file, zero-service, embedded, no server process for a print-shop desktop deployment). Rather than introducing a second embedded database with its own file and migration path, **Job History and Undo/Redo state are persisted in the same local SQLite database established in STEP-3.1**, in dedicated tables separate from `ministry_questions`/`ministry_questions_vec`.
- **Undo/Redo operates at the `ContentBlock`-edit level, scoped to `with_user_edit()` (STEP-1.1's sanctioned mutation path) only.** It does not attempt to undo AI classification results, extraction results, or InDesign-side operations — those are regenerated by re-running the relevant pipeline stage, not by an undo stack.
- **Undo/Redo is a single logical operation spanning both the in-memory `DocumentStore` and the SQLite history table — it is never split into an unlocked SQLite write followed by a separately-locked `DocumentStore` write, or vice versa.** The corrected sequence for both undo and redo is: `acquire DocumentStore.RLock → validate the history cursor against current in-memory state → replace the target block's snapshot in DocumentStore → persist the cursor's new position to SQLite → release DocumentStore.RLock`. This is the same lock `with_user_edit()` itself already requires to mutate `DocumentStore` safely (STEP-1.1) — undo/redo is simply another sanctioned mutation path through that same lock, not an exception to it. The prior draft's "never acquires the lock" claim only ever applied correctly to Job History and the Dashboard (STEP-6.9), which are pure SQLite reads/writes with no `DocumentStore` interaction — it was incorrectly generalized to Undo/Redo, which does touch `DocumentStore` by definition.
- **An in-memory undo/redo manager (a bounded list of pending edit actions for the currently-open document) sits in front of the SQLite table**, so that interactive Ctrl+Z/Ctrl+Y responsiveness does not require a database round-trip on every keystroke-level edit. The SQLite table remains the durable record (needed for Job History/Dashboard correlation and for reopening a document later), written when an edit is finalized (not on every intermediate keystroke) or when the document is saved/closed. The in-memory stack is discarded and rebuilt from SQLite when a document is reopened (see the recovery sequence below).

#### 3. Undo/Redo History Model — Cursor-Based, Not a Boolean Flag

A single `undone` boolean per row cannot represent linear history with branching. Consider: edit A → B → C, then undo twice (cursor back to A), then a *new* edit D is made from A. What happens to the now-orphaned B/C? A boolean flag has no way to express "B and C are no longer reachable via redo because a new branch was taken" versus "B and C are just temporarily undone and still redoable." The corrected model uses an explicit ordered sequence plus a current-position cursor, with an explicit branch-truncation rule:

```sql
-- migrations/002_job_history_and_undo.sql
-- Added to the same local SQLite database as STEP-3.1's ministry_questions
-- tables (%APPDATA%/Booklet_AI/question_bank.db) — no second database file.

CREATE TABLE job_history (
    id                      INTEGER PRIMARY KEY AUTOINCREMENT,
    source_file_path        TEXT NOT NULL,
    -- Post-review correction: the original single "source_file_hash"
    -- field was ambiguous between a binary hash of the source file on
    -- disk and STEP-1.1's compute_canonical_hash(), which operates on
    -- NFC-normalized extracted TEXT, not file bytes — these are
    -- different values computed by different functions over different
    -- inputs. Split explicitly so neither is mistaken for the other:
    source_file_sha256      TEXT NOT NULL,  -- SHA-256 of the raw source file bytes; identifies WHICH FILE this job was
    document_content_hash   TEXT,           -- STEP-1.1 compute_canonical_hash() of the extracted text tree, if applicable; identifies content integrity, not file identity
    page_count               INTEGER,
    status                   TEXT NOT NULL,  -- 'success' | 'failed' | 'in_progress'
    error_summary             TEXT,           -- translated (STEP-6.2) summary, if failed
    started_at               TEXT NOT NULL,
    completed_at              TEXT
);

-- Ordered edit sequence with an explicit cursor, replacing the prior
-- draft's single "undone" boolean, which could not represent
-- undo -> redo -> new-edit branching correctly.
CREATE TABLE block_edit_history (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    -- Nullable: an edit may occur in the preview/edit screen before the
    -- user has ever submitted a generation job for this document, i.e.
    -- before any job_history row exists yet. Populated retroactively
    -- once the document is submitted as a job (see Preconditions).
    job_id              INTEGER REFERENCES job_history(id),
    document_session_id TEXT NOT NULL,  -- groups edits belonging to one open-document session, independent of job_id
    sequence_index       INTEGER NOT NULL,  -- monotonically increasing position within this document_session_id
    block_id             TEXT NOT NULL,
    previous_content      TEXT NOT NULL,
    previous_hash          TEXT NOT NULL,
    new_content            TEXT NOT NULL,
    new_hash                TEXT NOT NULL,
    edited_at              TEXT NOT NULL,
    UNIQUE(document_session_id, sequence_index)
);

-- The current cursor position per open document session — the single
-- source of truth for "what is the current undo/redo position," rather
-- than inferring it from scattered boolean flags across rows.
CREATE TABLE edit_cursor (
    document_session_id TEXT PRIMARY KEY,
    current_sequence_index INTEGER NOT NULL  -- 0 = no edits applied; N = sequence_index N is the most recently applied edit
);
```

#### 4. Document-Reopen Recovery Sequence

The prior draft did not specify what happens when a document with recorded edit history is reopened after the application restarts — this is required, since `block_edit_history` alone does not answer "does this history still apply to the current extraction of this file?" The mandatory sequence:

1. On reopening a source file, recompute `source_file_sha256` (raw file bytes) and compare against the `job_history`/session record's stored value.
2. **If the hash matches:** re-run extraction (STEP-1.1–1.3) and classification (STEP-1.4) fresh, then replay `block_edit_history` rows for this `document_session_id` in `sequence_index` order, applying `with_user_edit()` for each — this reconstructs the edited state without ever trusting a stale in-memory snapshot.
3. **If the hash does not match** (the source file changed on disk since the recorded session): the recorded edit history is **not** silently applied — block identity (`block_id`) from the old extraction is not guaranteed to correspond to the same logical content in a re-extraction of a changed file. The user is shown a translated warning (STEP-6.2) that the source file has changed and prior edits could not be automatically reconciled, with the option to view the old history for manual reference or start fresh.

#### 5. Preconditions

- Job History and Undo/Redo must use the STEP-3.1 SQLite database file and migration runner — introducing a second embedded database file for this data is out of scope and not permitted without a new architectural decision.
- Undo/Redo entries are only ever created as a direct result of `ContentBlock.with_user_edit()` (STEP-1.1) — no other code path may write to `block_edit_history`.
- `block_edit_history.job_id` is nullable at insert time (edits may precede job submission) and must be backfilled with the corresponding `job_history.id` at the point the document is submitted as a generation job — a `document_session_id` value ties pre-job edits to their eventual job retroactively.
- Any function that mutates `DocumentStore` in response to undo/redo must acquire the same `threading.RLock` instance `with_user_edit()`'s caller already uses — a second, independent lock is not permitted, to avoid the two-lock deadlock/inconsistency class this correction exists to close.

#### 6. Acceptance Criteria

- **[AC-6.3.1]** Live Preview renders the current `DocumentStore` state without triggering any COM/InDesign call — verified by confirming no `win32com`/`pythoncom` import or call occurs anywhere in the preview code path.
- **[AC-6.3.1b]** Live Preview's `DocumentStore.RLock` acquisition is held only for the duration of copying the snapshot data needed for rendering — verified by confirming no Qt paint call, PDF-rendering call, or other I/O occurs between the lock's acquire and release in the preview code path.
- **[AC-6.3.2]** Every completed or failed job produces exactly one `job_history` row, with `status` and (on failure) `error_summary` populated using STEP-6.2's translated message, not a raw exception string.
- **[AC-6.3.3]** Calling `undo()` after a `with_user_edit()` call restores the block's `raw_content` and `content_hash` in `DocumentStore` to the pre-edit values recorded in `block_edit_history`, and decrements `edit_cursor.current_sequence_index` — both as part of one lock acquisition, not two independently-timed writes.
- **[AC-6.3.3b]** Given edit sequence A→B→C: undo twice (cursor at A), then a new edit D — `sequence_index` rows for B and C are deleted (branch truncation), and `redo()` after D is a no-op (there is no "future" to redo into) — verified directly against this exact scenario, the one the original boolean-flag model could not represent.
- **[AC-6.3.3c]** `undo()` refuses and surfaces a translated error (rather than overwriting state) if the target block's current hash in `DocumentStore` does not match the recorded `new_hash` for that history entry — verified by mutating the block out-of-band between edit and undo and confirming the refusal.
- **[AC-6.3.4]** No AI classification result or extraction result is ever written to or restorable from `block_edit_history` — verified by confirming only code paths originating in `with_user_edit()` write to this table.
- **[AC-6.3.5]** Job History and the Dashboard's (STEP-6.9) read/write operations never acquire `DocumentStore`'s `threading.RLock` — verified by confirming these code paths interact only with the SQLite connection. **This does not apply to Undo/Redo**, which correctly does acquire the lock per AC-6.3.3 — the two are no longer conflated.
- **[AC-6.3.6]** Reopening a source file whose `source_file_sha256` matches a recorded session correctly reconstructs the edited state by replaying `block_edit_history` in `sequence_index` order over a fresh extraction — verified end-to-end, not just that the replay function runs without error.
- **[AC-6.3.7]** Reopening a source file whose `source_file_sha256` does **not** match a recorded session never silently applies the old `block_edit_history` — verified by confirming the user is shown the translated mismatch warning and no `with_user_edit()` call happens automatically.
